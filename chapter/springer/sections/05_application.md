## 5 Application: The CAB Sepsis Monitor

To show how the gate fits into a hospital's adoption of an external model, we built a research prototype, the CAB Sepsis Monitor. A safety officer runs the gate before any alert reaches a ward, and clinicians later see which alerting system is in use and whether the gate certified it. The prototype has two screens, a deployment gate and a ward monitor. The figures show hospital A's model being installed at hospital B, using a random sample of 12,000 labelled patients drawn by the application from hospital B's training and validation patients, as in the experiments. The application splits them, within septic and non-septic patients, into a fit half and a certification half, exactly as in Algorithm 1. This sample differs from the one in Table 3, so its counts differ slightly; the figures quoted below are the application's own output for this sample.

### 5.1 Deployment Gate

The deployment gate collects the three inputs that CAB needs:

- **The hospital's requirements.** Two sliders set the sensitivity target and the additional false-alert rate the hospital will accept above the vendor's reported home rate.
- **Its labelled patients.** The user enters how many patients have been labelled and how they were chosen: a random sample, or a sample enriched so that half are septic. An enriched sample is valid for these tests when the septic and the non-septic patients are each sampled at random within their class, as the application does. The sensitivity test uses only the septic patients and the false-alert test only the non-septic patients, and the proof in Section 3.5 conditions on the numbers of each. A convenience sample enriched for sepsis, such as patients selected because clinicians suspected it, would not meet this condition.
- **What arrived with the model.** A panel shows the vendor's threshold, the home validation counts the vendor reports and the limits these imply at the receiving hospital.

Running the gate produces the decision as a coloured banner, followed by the evidence for each option in order of intervention: the counts, the exact one-sided bounds at level α/4 and whether each test passed. In Fig. 7, keeping the model fails because its sensitivity can be certified only to be at least 62.3%. Calibration certifies 80% sensitivity but fails the false-alert test, with an upper bound of 63.2% against a limit of 45.1%. The adapted model passes both tests, with a lower bound of 80.2% for sensitivity and an upper bound of 37.1% for false alerts, and is deployed.

Because the prototype runs on retrospective data, it can also show what each choice would have done on the 8,000 patients of the receiving hospital that were not labelled: its 4,000 remaining training and validation patients and all 4,000 of its test patients. These patients play no part in any decision of the gate, which uses only the labelled patients, and this check is not available in real deployment. It is an empirical comparison, separate from the certification bounds, which come from the labelled patients alone. In this sample the adapted model detected 84.5% of septic patients and alerted 35.4% of non-septic patients, meeting both requirements. The imported model as supplied detected only 68.2%. A recalibration without certification, whose threshold was set to reach 80% sensitivity on the labelled patients, appeared to alert 55.7% of non-septic patients there and alerted 55.6% of the unseen ones, violating the false-alert limit; it would have been rejected by CAB's test.

### 5.2 Ward Monitor

The ward monitor (Fig. 8) replays the receiving hospital's test patients, hour by hour, with whatever configuration the gate deployed. These patients are part of the 8,000 used in the retrospective check above, so none of them was labelled, used to fit a model or used by the gate. For illustration, each ward is a sample of 16 test patients with at least 12 hours in the ICU, 4 of them septic. If the gate blocked, the monitor uses the modified NEWS2 score with a cut-off of 5 instead. A header states which alerting system is in use and whether the gate certified it against the hospital's configured requirements; certification in this sense is not a demonstration of clinical safety or benefit.

The ward table lists each bed with the current score relative to the alert threshold, the alert status and how long the alert has been active, and a 24-hour trend. The patient view plots the risk score against the threshold, together with the main vital signs and laboratory results, so that a clinician can see what preceded an alert. A switch, available only in this simulation, reveals the recorded onset of sepsis.

### 5.3 Engineering

- **One code path.** The application calls the same gate implementation as the experiments. An automated test compares the application's decision function with the experiment's on 3,000 randomly generated cases covering all four outcomes (534 KEEP, 1,088 CALIBRATE, 740 ADAPT and 638 BLOCK); the decisions and thresholds were identical in every case. This test covers the decision function, not the whole interface.
- **Local operation.** The application runs on a single workstation, and no patient data leave it; this alone does not establish compliance with any data-protection or regulatory requirement.
- **The vendor package as a specification.** The gate needs only the model, its threshold and its home validation counts. A vendor that also publishes its full home operating curve allows the hospital to plan its labels with the calculator of Section 3.8 before it starts labelling.
- **Limitations.** The prototype uses public retrospective data and is not intended for clinical use. Integration with an electronic health record, for example through HL7 FHIR, monitoring after deployment and prospective evaluation would all be needed before any clinical use.
